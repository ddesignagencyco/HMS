================================================================================
START CODE ON THE CUSTOMER'S SCREEN - FRONTEND IMPLEMENTATION
Backend endpoint is built, tested and deployed on this branch.
================================================================================

THE PROBLEM
-----------
To start a job the provider must enter a 6-digit code that the CUSTOMER gives
them at the door. Until now the only place that code existed was an SMS sent
when the booking was accepted - possibly days earlier, for a job booked weeks
out, and buried under every other message since.

The fix is on the backend. Your job is to show the code in the customer's app.


THE ENDPOINT
------------
  POST /api/v1/bookings/{id}/start-code

  Auth:    Bearer token, CUSTOMER role
  Body:    none
  Query:   none

  200 response:

    {
      "code": "418273",
      "expiresInSeconds": 900
    }

That is the whole contract. Send no body.


HOW IT WORKS (so you don't get this wrong)
------------------------------------------
1. It does NOT return the old code. It generates a NEW one every call.
   The stored code is a hash and cannot be read back - by anyone, including
   us.

2. Each new code INVALIDATES the previous one. There is only ever one
   current code per booking.

   >>> THIS IS THE MAIN FOOTGUN <<<
   If the customer taps "refresh" while the provider is typing the old code,
   the code they are typing stops working. So:
     - Show the code. Do NOT poll or auto-refresh it.
     - Make any refresh a deliberate tap, not a background fetch.
     - If you do refresh, the provider needs the new one - and they also get
       a fresh SMS, so there is always a second copy.

3. The customer only. A provider calling this gets 403 and the request never
   reaches the service layer. If you are ever tempted to put this on the
   provider's screen: don't. It is the customer authorising the work - that is
   the entire point.

4. Once the job has started there is nothing left to authorise:
     409 CONFLICT, detail "This job has already been started..."
   So hide the button once status is IN_PROGRESS or later.

5. The SMS still works exactly as before. The existing messaging is unchanged.
   This endpoint is an additional channel, not a replacement.


STATUS CODES
------------
  200  { code, expiresInSeconds }   new code issued and shown
  403  FORBIDDEN                    caller is not a customer (guard rejects
                                    before any lookup, so this is returned
                                    identically for a booking that does not
                                    exist - nothing leaks)
  404  NOT_FOUND                    the booking is not this customer's
  409  CONFLICT                     the job has already been started


SUGGESTED UX
------------
Where it belongs: the customer's booking detail / "today's job" screen, and
on the in-app message thread if you have one.

  - Large, high-contrast, fixed digits (the provider reads it across a doorway
    in daylight - six large digits beats a normal-weight input).
  - The provider is often standing there waiting. Label it plainly:
    "Give this code to your provider when they arrive."
  - A "Show code" / "Refresh" button. Not automatic.
  - Consider also offering "Send me an SMS" - it re-issues and re-sends, which
    is the same call, and is a good fallback when the customer is on the spot
    without their phone.


TESTING
-------
Backend tests cover: the code actually starts the job, the SMS still fires, the
code is never stored in plaintext, a provider is refused, another customer is
refused, a re-issue invalidates the old code, and 409 after the job starts.

Please test the flow end to end in the real UI:
  1. Accept a booking, mark en route.
  2. Customer opens the app, taps to see the code.
  3. Provider enters it -> job starts.
  4. Tap refresh, confirm the OLD code no longer works and the NEW one does.

Step 4 is the one that bites.
